=== cpu bottlenecks

* link:https://docs.vulkan.org/guide/latest/profiling.html#_cpu_side_bottlenecks[cpu bottlenecks]

. command recording overhead
.. **use secondary cmd buffer**: parallelize recording commands across multiple cpu threads
.. **sort draw calls**: reduce overhead usage of vkCmdBindPipeline, since it triggers internal driver state updates(performance impact)
.. **use descriptor indexing or buffer or heap**: reduce high cpu time on calling vkUpdateDescriptorSets
. submission and synchronization
.. **batch submit command buffers**: vkQueueSubmit has a high fixed cost. don't prequently submit small amounts of work
.. **avoid device and queue wait idle in main loop**: forcing cpu wait until gpu is completely empty. **use a ring buffer of fences** to track frame completion, and keep the gpu fed with work for future frames

=== gpu bottlenecks

when frame time is dominated by GPU execution rather than cpu wait time

==== hardware metrics

. occupancy: ratio of active "warps" or "wavefronts"(groups of threads)
.. low occupancy often means shaders are **using too many registers**, preventing the gpu from hiding latency
. stalls: occurs when gpu's execution units(ALUs) are waiting for data
.. memory stall: waiting for data to arrive from VRAM or L2 cache
.. execution stall: waiting for a previous instruction to finish(e.g. a long-latency math operation)
. bandwidth utilization(带宽利用率): high utilization of the memory controller indicates "memory bound"

==== common gpu issues

. vertex bound: too many vertices or inefficient vertex fetch, use **VK_EXT_mesh_shader** to replace traditional vertex pipeline if geometry is the bottleneck
. frag bound(fill rate): high overdraw is the most common cause
.. early-z
.. overdraw analysis: use renderdoc's overdraw overlay to find areas where the same pixel is shaded multiple times
. bandwidth bound: caused by large, uncompressed textures, or too many render target attachments
.. use texture compression(ASTC, BCn)
.. use VK_ATTACHMENT_LOAD_OP_CLEAR instead of manual vkCmdClearColorImage to allow the hardware to optimize memory bandwidth

==== syncrhonization bubbles

bubble means a period where the GPU is idle because it is waiting for a synchronization dependency that hasn't been met yet.

. use Nsight/RGP etc to show the GPU timeline, if you see large gaps between workloads where no queues are active, you have a bubble
. root causes:
.. restrictive barriers: over restrictive barrier like VK_PIPELINE_STAGE_ALL_COMMANDS_BIT, forces wait for all previous work to finish before starting next task
.. cpu-gpu sync: cpu submitting not fast enough, or cpu is waiting for a fence too early

== loader

=== what is loader

The loader is critical to managing the proper dispatching of Vulkan functions to the appropriate set of layers and drivers

. Support one or more Vulkan-capable drivers on a user's system without them interfering with one another
. Support Vulkan Layers which are optional modules that can be enabled by an application, developer, or standard system settings
. Keep the overall overhead of the loader to the minimum possible

=== loader linking

vulkan sdk provides a pre-built loader for Windows

. directly linking
.. dynamic(连接到一个dll): the loader is a dynamic library, e.g. "dll" on windows, "so" on linux, etc.
... applications can usually expect a copy of the loader to be present on a system(windows, linux)
...  If applications want to be completely sure that a loader is present, they can include a loader or runtime installer with their application
.. static: **This was removed and is no longer possible**
... because of changes to the driver which made older applications that statically linked unable to find newer drivers
... The loader can never be updated without re-linking the application
... Could cause conflicts between the different loader versions across different libraries
. indrectly linking(只导出函数到dispatch table，库在编译时动态检测并链接): apps can use the appropriate platform-specific dynamic symbol lookup on the loader library to initialize the application's own dispatch table
.. allows an application to fail gracefully if the loader cannot be found
.. provides the fastest mechanism for the application to call Vulkan functions

== queues

* commands sumbmitted in order, but can process independently and out of order
* commands in different queues are inrelative, unless using VkSemaphore to sync
* operation of submitting to queue is serial, but can submit to different queue simultaneously
* VkQueue cannot expose details of mapped hardware implementations, it's depends on GPU implementations
* not all app's will require or benefit from multiple queues, check specific gpu's manual!

== queue family

* a set of VkQueues that have common props and support the same functionality

. VK_QUEUE_GRAPHICS_BIT: used for vkCmdDraw* and graphics pipeline commands

== threading

* https://docs.vulkan.org/spec/latest/chapters/fundamentals.html#fundamentals-threadingbehavior

this section is valuable, should revisit after complete other books

* multithreading in Vulkan only provides host-side scaling, as anything interacting with the device still needs to be synchronized correctly
* Vulkan implementations are not supposed to introduce any multi-threading, so if an app wants multi-CPU performance, the app is in charge of managing the threading

* command pool: must not be accessed simultaneously from multiple threads
** By using a separate command pool in each host-thread the application can create multiple command buffers in parallel without any costly locks
* descriptor pool: By creating multiple descriptor pools, each application host thread is able to manage a descriptor set in each descriptor pool at the same time

== common pitfalls

this section is worth to read

* [x] always enable validation layers when develop
* [ ] There is rarely a “perfect” solution and obsessing over finding one is often a fruitless effort
. try to create an adequate solution that meets the current needs and isn’t overly convoluted
. While the specification for Vulkan can be useful, it isn’t the best source for how to use Vulkan in practice
. reference external sources, like this guide, hardware best practice guides, tutorials, and other articles for more in-depth information
. profiling various solutions is an important part of discovering which solution to use
* [ ] command buffer re-using may have no performance benefit for now(not as some old tutorials tells), it's not that simple! additionally, the implementation of re-use increase the complexity of development, because draw calls with dynamic scene objects lets computed data varies.
** prefer to re-record command buffers every frame is more adequate
** if performance is a problem, recording with multithreaded, as well as using secondary command buffers for non-variable draw calls, e.g. post-processing
* optimize pipeline creating and swapping only when needed. it depends on how complexity of rendering and scene
* do not duplicate resources for each swapchain's image, it's flexible, some resource don't need that much as number of swapchain images
* not necessary to use multiple queues in one queue family, it depends on hardware, see vendor's manual
* descriptor set can be used not only one, vulkan spec mandates hardware support at least 4 at a time, as most hardware supporting at least 8(**so, how to manage ds set?**)
